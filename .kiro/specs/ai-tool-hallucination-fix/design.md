# AI Tool Hallucination Fix - Bugfix Design

## Overview

The AI auto-apply system is experiencing critical failures due to the AI model (qwen2.5:3b) hallucinating non-existent tool names instead of using the six actual browser interaction tools. This bug manifests in a dual-AI architecture where the Planner Agent and Browser Agent both lack sufficient constraints and validation to prevent tool name hallucination. The fix will implement a multi-layered defense strategy: (1) explicit tool listing in prompts, (2) strict tool name validation before execution, (3) active error feedback to the AI when hallucinations occur, and (4) fail-fast termination after repeated hallucinations. This approach ensures the AI is constrained to valid tools, receives immediate correction when it hallucinates, and prevents infinite loops of invalid tool calls.

## Glossary

- **Bug_Condition (C)**: The condition that triggers the bug - when the AI model generates a tool call with a name that is NOT in the allowed set: `click_element`, `enter_text`, `select_option`, `upload_file`, `press_key`, `navigate`
- **Property (P)**: The desired behavior when the AI generates tool calls - all tool names must be from the allowed set and execute successfully
- **Preservation**: Existing valid tool execution behavior that must remain unchanged by the fix
- **Hallucination**: When the AI model invents tool names that don't exist in the system (e.g., `apply_for_job`, `custom_search_engine`)
- **Dual-AI Architecture**: The two-step AI process where Planner Agent decides what to do, and Browser Agent executes the actions
- **ALLOWED_TOOLS**: The strict set of six valid tool names: `click_element`, `enter_text`, `select_option`, `upload_file`, `press_key`, `navigate`
- **HALLUCINATION_ERROR**: A new error type indicating the AI attempted to use an invalid tool name
- **Correction Message**: Feedback injected into the AI's next iteration when a hallucination is detected, listing valid tools and requesting retry
- **Fail-Fast Check**: Termination logic that stops execution after 3 consecutive hallucinations to prevent infinite loops

## Bug Details

### Bug Condition

The bug manifests when the AI model (qwen2.5:3b) generates a tool call with a name that does not exist in the system's tool definitions. The Browser Agent's `_execute_step_legacy()` method attempts to execute the hallucinated tool name without validation, resulting in execution failure. The system then continues to the next iteration without providing corrective feedback to the AI, leading to repeated hallucinations across 7+ iterations.

**Formal Specification:**
```
FUNCTION isBugCondition(tool_call)
  INPUT: tool_call of type Dict[str, Any] with keys "name" and "arguments"
  OUTPUT: boolean
  
  ALLOWED_TOOLS = {'click_element', 'enter_text', 'select_option', 
                   'upload_file', 'press_key', 'navigate'}
  
  RETURN tool_call["name"] NOT IN ALLOWED_TOOLS
         AND tool_call is generated by AI model
         AND system attempts to execute tool_call
END FUNCTION
```

### Examples

**Example 1: Hallucinated Tool - apply_for_job**
- **Input**: AI generates `{"name": "apply_for_job", "arguments": {"job_id": "12345"}}`
- **Expected**: System rejects the tool call, returns HALLUCINATION_ERROR, and provides correction message
- **Actual (Unfixed)**: System attempts to execute, fails silently, continues to next iteration

**Example 2: Hallucinated Tool - custom_search_engine**
- **Input**: AI generates `{"name": "custom_search_engine", "arguments": {"query": "Software Engineer"}}`
- **Expected**: System rejects the tool call, returns HALLUCINATION_ERROR, and provides correction message
- **Actual (Unfixed)**: System attempts to execute, fails silently, continues to next iteration

**Example 3: Valid Tool - click_element**
- **Input**: AI generates `{"name": "click_element", "arguments": {"mmid": "123"}}`
- **Expected**: System validates tool name, executes successfully
- **Actual (Unfixed)**: System executes successfully (this behavior must be preserved)

**Example 4: Multiple Hallucinations in Sequence**
- **Input**: AI generates hallucinated tools in iterations 1, 2, 3, 4, 5, 6, 7
- **Expected**: System detects pattern after 3 consecutive hallucinations and terminates with clear error
- **Actual (Unfixed)**: System continues indefinitely, wasting 20-25 seconds per iteration

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- Valid tool calls (`click_element`, `enter_text`, `select_option`, `upload_file`, `press_key`, `navigate`) must continue to execute successfully
- DOM analysis and element detection must remain unchanged
- Ollama API integration must continue to work correctly
- MCP and legacy execution modes must both continue to function
- Logging and structured logging must continue to capture all interactions
- Retry logic for recoverable errors must remain unchanged
- Screenshot capture on failures must remain unchanged

**Scope:**
All inputs that do NOT involve hallucinated tool names should be completely unaffected by this fix. This includes:
- Correct tool calls with valid names and arguments
- DOM state analysis and parsing
- AI prompt construction and response parsing
- Network monitoring and error classification
- Career page navigation and validation

## Hypothesized Root Cause

Based on the bug description and test results, the most likely issues are:

1. **Missing Tool Constraints in Prompts**: The Planner Agent's `SYSTEM_PROMPT_BASE` and Browser Agent's `SYSTEM_PROMPT` do not explicitly list the available tools at the beginning with strong warnings against inventing tool names. The small model (qwen2.5:3b) lacks the reasoning capability to infer tool constraints from the tool definitions alone.

2. **No Tool Name Validation**: The Browser Agent's `_execute_step_legacy()` method directly attempts to execute tool calls without validating that the tool name exists in `ALLOWED_TOOLS`. This allows hallucinated tool names to reach the execution layer where they fail silently.

3. **Passive Error Feedback**: When a tool execution fails (including hallucinated tools), the error is logged but not actively fed back to the AI in the next iteration. The AI receives no correction message indicating "you used an invalid tool name, here are the valid ones."

4. **No Fail-Fast Logic**: The FSM orchestrator in `orchestrator.py` does not detect patterns of repeated hallucinations. It continues iterating up to `max_iterations` (20) even when the AI is stuck in a hallucination loop, wasting 20-25 seconds per iteration.

5. **Dual-AI Complexity**: The two-step architecture (Planner → Browser Agent) increases the hallucination risk because the Planner Agent decides "what to do" without seeing the Browser Agent's tool definitions, and the Browser Agent executes without validating against the Planner's intent.

## Correctness Properties

Property 1: Bug Condition - Tool Name Validation

_For any_ tool call generated by the AI where the tool name is NOT in the allowed set (`click_element`, `enter_text`, `select_option`, `upload_file`, `press_key`, `navigate`), the fixed system SHALL reject the tool call, return a HALLUCINATION_ERROR result, and inject a correction message into the next AI iteration listing the valid tools.

**Validates: Requirements 2.2, 2.3**

Property 2: Preservation - Valid Tool Execution

_For any_ tool call generated by the AI where the tool name IS in the allowed set, the fixed system SHALL execute the tool exactly as the original system did, preserving all existing functionality for valid tool calls including error handling, retry logic, and logging.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 3.5, 3.6**

1. **Define ALLOWED_TOOLS Constant**: Add a class-level constant at the top of `BrowserAgent` class listing the six valid tool names:

   ```python
   }
   ```

2. **Implement validate_tool_call() Method**: Add a new method to validate tool names before execution:
   ```python
   def validate_tool_call(self, tool_call: Dict[str, Any]) -> tuple[bool, Optional[str]]:
       """
       Validate that tool_call uses an allowed tool name.
       
       Returns:
           (is_valid, error_message)
       """
       tool_name = tool_call.get("name", "")
       if tool_name not in self.ALLOWED_TOOLS:
           return False, f"Invalid tool '{tool_name}'. Allowed tools: {', '.join(sorted(self.ALLOWED_TOOLS))}"
       return True, None
   ```

3. **Update _execute_step_legacy() to Validate Tool Names**: Modify the method to call `validate_tool_call()` before attempting execution. If validation fails, return a result with `error_type="HALLUCINATION_ERROR"`:

   ```python
   if not is_valid:
       logger.error(f"Tool hallucination detected: {error_msg}")
       return {
           "success": False,
           "error": error_msg,
           "error_type": "HALLUCINATION_ERROR",
           "tool_name": tool_call.get("name", "unknown")
   ```

## Testing Strategy

### Validation Approach

The testing strategy follows a two-phase approach: first, surface counterexamples that demonstrate the bug on unfixed code, then verify the fix works correctly and preserves existing behavior.

### Exploratory Bug Condition Checking

**Goal**: Surface counterexamples that demonstrate the bug BEFORE implementing the fix. Confirm or refute the root cause analysis. If we refute, we will need to re-hypothesize.

**Test Plan**: Write tests that mock the AI to return hallucinated tool names (e.g., `apply_for_job`, `custom_search_engine`) and observe how the UNFIXED system handles them. Run these tests on the UNFIXED code to observe failures and understand the root cause.

**Test Cases**:
1. **Single Hallucination Test**: Mock AI to return `{"name": "apply_for_job", "arguments": {}}` and verify the unfixed system attempts to execute it without validation (will fail on unfixed code)
2. **Multiple Hallucinations Test**: Mock AI to return different hallucinated tools across 3 iterations and verify the unfixed system does not terminate early (will fail on unfixed code)
3. **No Correction Feedback Test**: Mock AI to hallucinate, then verify the next AI call does not receive a correction message (will fail on unfixed code)
4. **Valid Tool Test**: Mock AI to return `{"name": "click_element", "arguments": {"mmid": "123"}}` and verify it executes successfully (should pass on unfixed code - this is preservation)

**Expected Counterexamples**:
- Hallucinated tool names are not validated before execution
- System attempts to execute non-existent tools and fails silently
- No correction messages are injected into subsequent AI iterations
- System continues iterating indefinitely without detecting hallucination patterns
- Possible causes: missing validation logic, missing prompt constraints, missing fail-fast logic

### Fix Checking

**Goal**: Verify that for all inputs where the bug condition holds (hallucinated tool names), the fixed function produces the expected behavior (rejection + correction).

**Pseudocode:**
```
FOR ALL tool_call WHERE isBugCondition(tool_call) DO
  result := browser_agent_fixed.execute_step(tool_call)
  ASSERT result["success"] == False
  ASSERT result["error_type"] == "HALLUCINATION_ERROR"
  ASSERT "Valid tools are:" IN result["error"]
END FOR
```

**Test Cases**:
1. Test with `apply_for_job` - verify rejection
2. Test with `custom_search_engine` - verify rejection
3. Test with `generate_job_ad_template` - verify rejection
4. Test with any arbitrary invalid tool name - verify rejection
5. Test that correction message is injected into next iteration context

### Preservation Checking

**Goal**: Verify that for all inputs where the bug condition does NOT hold (valid tool names), the fixed function produces the same result as the original function.

**Pseudocode:**
```
FOR ALL tool_call WHERE NOT isBugCondition(tool_call) DO
  ASSERT browser_agent_original.execute_step(tool_call) = browser_agent_fixed.execute_step(tool_call)
END FOR
```

**Testing Approach**: Property-based testing is recommended for preservation checking because:
- It generates many test cases automatically across the input domain
- It catches edge cases that manual unit tests might miss
- It provides strong guarantees that behavior is unchanged for all valid tool calls

**Test Plan**: Observe behavior on UNFIXED code first for valid tool calls, then write property-based tests capturing that behavior.

**Test Cases**:
1. **Valid Tool Execution Preservation**: Verify `click_element`, `enter_text`, `select_option`, `upload_file`, `press_key`, `navigate` all execute successfully after fix
2. **Error Handling Preservation**: Verify recoverable errors (timeouts, missing elements) are still handled with retry logic
3. **Logging Preservation**: Verify all tool calls are still logged correctly
4. **MCP Mode Preservation**: Verify MCP execution mode continues to work
5. **Legacy Mode Preservation**: Verify legacy execution mode continues to work
